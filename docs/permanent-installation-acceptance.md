# Persistent installation acceptance

Observed on 2026-11-10 using a Linux viewer/runtime host and a Mac VM host.
This records direct private-network SSH and process/container persistence,
not physical-host reboot acceptance. Deployment identities, keys, tokens and
private runtime records are excluded.

## Connection and runtime account

- The configured restricted key reached the Mac's normal SSH endpoint directly,
  without the fresh laptop's temporary listener or reverse tunnel.
- The fixed status command returned running/ready; `uname -a` was refused with
  `unsupported_operation`. Host-key verification and forced-command restrictions
  remained enabled.
- SSH under the container's default root account initially failed to resolve the
  configured alias; the actual runtime account's passwd home contained the SSH
  configuration. The generic guide now requires account/home checks and explicit
  Docker exec user selection. No account name is assumed by the plugin.
- A clean test image's runtime UID differed from the existing persistent mounts'
  owner, and installation failed rather than modifying inaccessible directories.
  A locally derived, pinned test image aligned its existing runtime account and
  primary group with the operator-owned mounts. No production file ownership,
  key permissions or control-directory protections were relaxed.
- A separate container installed into a new Hermes home using only the selected
  restricted identity and verified host keys. Native doctor and plugin validation
  passed. All clients targeting the same VM shared the existing control directory.

## Supervised viewer

The viewer was moved from an unsupervised foreground command to an explicitly
enabled systemd **user** service generated by `render-viewer-service.py`.
`systemd-analyze --user verify` accepted the generated unit. The service uses a
versioned source export at `5bd1a3aa6667fcfa4a396ec93f527afc471da3bf`, with a private
branch/commit receipt. Later changes in this PR are documentation-only. Source
and runtime state are separate; editing a feature checkout no longer changes
the running service's assets.

With no active write and control paused:

- The old viewer exited normally before the service started; no second viewer
  was allowed to compete for the control directory.
- The service was enabled and active. A further `systemctl --user restart`
  returned it to active/running. Browser access credentials rotated; the old
  token returned HTTP 403 and the new token authenticated successfully.
- Controller, generation and pending state were identical before and after.
  No transfer, uncertainty acknowledgement, guest lifecycle or GUI input occurred.
- A new independent SSH session confirmed the service was still active and the
  access helper authenticated. No browser stream was open during the final
  combined check; the service does not require a browser tunnel to stay running.
- The host already had user-manager lingering enabled; this test did not change
  that policy. Neither enabled service state nor lingering proves physical-boot
  recovery, which remains untested.

## Container recreation and final readiness

The isolated test container was stopped and removed without deleting its bind
mounts, then recreated from the same pinned image and configuration. Installed
plugin, installer receipt and Hermes configuration hashes matched. The shared
lease also matched. The normal SSH status probe, arbitrary-command refusal,
Hermes plugin validation and native doctor passed again.

The test container uses an idle process for explicit CLI validation; it is not
proof of unattended model/gateway startup. Production deployments must retain
their supported Hermes startup command and model configuration. The container's
restart policy and persistent mounts do not by themselves certify host reboot.

The host-side combined onboarding check passed native readiness, authenticated
loopback HTTP, viewer assets/dependencies and the optional shared VNC handshake.
Warnings correctly retained intentional paused control, absent browser stream
and the manual external-firewall check. No new browser input or model-driven
claim is made in this phase; those results are recorded separately in
[laptop acceptance](laptop-acceptance.md) and [hardware acceptance](hardware-acceptance.md).

Validation at the implementation commit: 214 Python tests; macOS 192 passed / 22
expected Hermes-only skips, Hermes 204 passed / 10 expected macOS-only skips.
The full Hermes CI gate passed repeatable bundles, extracted-package validation,
fresh install and synthetic offline upgrade. The Node pointer regression passed.

No physical host or guest was rebooted. Physical-host reboot/firewall persistence,
naming review, exact release-candidate testing and public distribution remain
on the [release checklist](release-readiness.md).
